# 🧺 Sokuri

<b>소쿠리(Sokuri)</b>는 사용자가 URL만 입력하면 가방 사이즈를 기반으로 물건을 넣어볼 수 있는 **IOS 애플리케이션**입니다.<br>
실제 가방이 없어도, 모바일 기기에서 다양한 물건을 넣어보며 수납 가능 여부를 시각적으로 확인할 수 있습니다.

# Motivation

### 온라인 쇼핑에서 겪은 불편함을 개선해보자

기획 과정에서 온라인 쇼핑 중 가방 구매 시 겪었던 불편함이 떠올랐습니다. 대부분의 쇼핑몰은 가방의 가로 **·** 세로 **·** 높이 수치나 착용 이미지가 제공되지만, 물건들이 들어가는지는 확인하기 어렵습니다. 리뷰를 참고하거나, 직접 구매 후 확인하는 수밖에 없었습니다.

이러한 불편함을 줄이기 위해, 기능을 직접 개발해보기로 결정했습니다. **사용자가 URL을 입력하면 가방의 실제 사이즈를 추정하고, 다양한 물건을 넣어보는 시뮬레이션 기능**을 통해 수납이 가능한지 확인할 수 있도록 구성했습니다.

### 앱 환경에 맞는 사용자 경험을 직접 설계하고 구현하다

가방을 구매할 때, 모바일 환경에서 가방 정보를 확인하고, 비교하여 구매를 결정하는 일이 많았습니다. 이런 사용흐름을 고려했을 때, 앱에서 바로 링크를 붙여넣고 수납 여부를 확인할 수 있는 구조가 자연스럽고 편리하다고 생각했습니다.

앱은 터치와 제스처를 중심으로 작동하기 때문에, **사용자는 화면을 누르면 곧바로 반응이 돌아오기를 기대**합니다. 이러한 기대를 충족시키기 위해서는 **빠르고 직관적인 피드백 설계**가 필요하다고 느꼈고, 개발 과정에서 차이를 직접 체감해보고 싶었습니다.

이번 개인 프로젝트는 **세 가지**를 **주요 목표**로 설정했습니다.<br>

**1. 제스처 기반 UI/UX를 직접 설계하고 구현하기<br> 2. URL 입력 → 가방 사이즈 추정 → 시뮬레이션 시각화로 이어지는 전체 흐름 구현하기<br> 3. 기존 웹 개발 경험을 앱 환경에 맞게 재구성하고 확장하기<br>**

웹 기반 개발 경험을 앱 환경에서 어떻게 활용할 수 있을지, 그리고 어떤 예상치 못한 기술적 도전이 나타나는지를 직접 경험해보고 싶었습니다.

# Tech stack

### 어플리케이션

- **개발 언어**: React Native
- **iOS 환경**: Xcode (iOS 17), WebView 기반 UI
- **상태 관리**: Zustand
- **3D 시뮬레이터**: Three.js (WebView 내 React 렌더링)
- **오픈 소스 라이브러리**: react-native-webview, react-native-gesture-handler, react-native-reanimated 등

### 서버 및 크롤링

- **웹 프레임워크**: FastAPI
- **크롤링 도구**: Puppeteer (Node.js)
- **API 통신 방식**: RESTful API

### 머신러닝 및 이미지 분석

- **개발 환경**: Python
- **딥러닝 프레임워크**: YOLOv8 (Ultralytics)
- **딥러닝 모델 포맷**: PyTorch (.pt)

# Development

## 1. 후기 이미지에서 어떻게 실제 사이즈를 추정할 수 있을까?

**온라인 쇼핑몰에서는** 가방의 가로 **·** 세로 **·** 높이 같은 수치 정보만 제공하는 경우가 많아, **실제로 사용하는 물건들이 가방에 들어가는지 판단하기 어렵습니다.** 이 문제를 해결하기 위해, 후기 이미지 속 가방과 참조 가능한 물체의 상대 크기를 분석해 실제 가방 사이즈를 추정하고, 이를 기반으로 수납 시뮬레이션을 제공합니다.

이때 **기준 객체**를 활용합니다. 기준 객체는 이미지 속에서 크기가 명확히 알려진 물체로 손, 신용카드, A4 용지, 스마트폰 등이 해당됩니다. 이러한 기준 객체의 실제 크기를 알고 있으면, 사진 속에서 가방과의 픽셀 단위 크기 차이를 비교해 **실제 크기(cm)** 로 환산할 수 있습니다.

기준 객체와 가방을 찾기 위해, YOLOv8 모델을 사용합니다.

> YOLO(You Only Look Once)는 이미지에서 특정 물체가 어디에 있는지를 빠르게 탐지하는 인공지능 기술입니다.
> 이미지를 한 번만 분석해 다양한 객체의 위치와 종류를 동시에 찾아낼 수 있는 것이 특징입니다.

YOLOv8을 통해 후기 이미지에서 가방과 기준 객체를 탐지하고, 기준 객체가 있을 경우 두 객체의 상대 크기를 비교해 가방의 실측 크기를 추정합니다. 기준 객체가 없는 경우에는 카테고리별 평균 데이터를 바탕으로 보정값을 적용해 사이즈 추정을 보완합니다.

### 1.1 후기 이미지를 크롤링하고 분석해 실제 사이즈를 추정

사용자가 입력한 URL을 통해 해당 쇼핑몰의 후기 이미지를 크롤링합니다. 현재는 무신사와 지그재그를 지원하며, 각 쇼핑몰의 구조에 맞게 크롤러를 구성해 후기 이미지들을 수집합니다.

이후 YOLOv8 모델을 활용해 이미지에서 가방과 기준 객체를 탐지합니다.

기준 객체가 함께 있을 경우, 픽셀 단위의 크기를 실측 단위(cm)로 환산할 수 있어 정확한 추정이 가능합니다. 기준 객체가 없다면 카테고리별로 수집된 평균 사이즈 데이터를 기반으로 보정값을 적용합니다.

### 1.2 후기 이미지가 없는 경우 사용가 직접 입력하도록 보완

후기 이미지가 존재하지 않거나, 기준 객체가 함께 찍힌 이미지가 충분하지 않을 경우에는 시뮬레이션을 위한 가방 사이즈 추정이 불가능해지는 문제가 발생합니다.

해당 상품에 후기가 없거나 이미지가 부족한 경우, 사용자가 직접 사이즈를 입력할 수 있도록 폼을 제공합니다. 입력된 값은 즉시 WebView 기반 시뮬레이터로 전달되어, 실시간으로 가방 모델이 업데이트되고 수납 가능 여부를 확인할 수 있습니다.
대체 입력 경로를 마련함으로써, 이미지가 부족한 상품에 대해서도 직접적인 비교를 제공할 수 있도록 구성했습니다.

### 1.3 매번 사용자가 아이템을 등록해야 할까?

자주 사용되는 아이템들(노트북, 책, 텀블러 등)은 미리 등록되어 있습니다. 사용자는 해당 목록에서 선택만 하면 됩니다. 필요한 경우 아이템을 직접 등록할 수 있고, 등록한 아이템의 사이즈 변경도 가능합니다. 사용자의 입력 부담을 줄이면서 사이즈 변경 등 유연성을 확보했습니다.

## 2. React Native에서 3D 시뮬레이션 구현이 가능할까?

React Native에서 3D 시뮬레이션을 구현하려면 몇 가지 기술적 제약을 먼저 해결해야 했습니다.
모바일 앱은 대부분 2D 기반 UI에 최적화되어 있어, 버튼 클릭이나 목록 스크롤 같은 기능은 쉽게 구현할 수 있습니다.
**가방 안에 물건이 실제로 들어가는지**를 시각적으로 확인해야 하는 3D 시뮬레이션 기능은 별도의 구현 방식이 필요했습니다.

### 2.1 문제: React Native는 3D 시뮬레이션에 적합하지 않다

가방 안에 물건을 넣고 빼보는 3D 장면을 만들기 위해서는 일반적으로 **Three.js**나 **WebGL** 같은 전문적인 3D 그래픽 도구가 필요합니다.
Three.js는 웹에서 3D 그래픽을 구현할 수 있도록 도와주는 자바스크립트 기반의 도구이고, WebGL은 그 기반이 되는 기술로 컴퓨터가 입체 장면을 그릴 수 있게 해줍니다.

구현 과정에서 마주한 문제는 React Native만으로는 원하는 수준의 3D 시뮬레이션을 직접 구현하기 어렵다는 점이었습니다. React Native의 네이티브 실행 환경에서는 입체적인 3D 그래픽을 렌더링하는 기능은 제공하지 않았습니다. 이를 해결하기 위해 3D 기능을 구현할 수 있는 다른 방법들을 찾아보게 되었고, 개발 시간, 안정성, 유지보수 기준으로 프로젝트에 적용 가능한 방법을 결정하기 위해 아래 세 가지 대안을 비교해보았습니다.

### 2.2 기술 선택 과정: WebView를 선택한 이유

#### 방법1. React Native 전용 3D 엔진을 사용

React Native에서 직접 3D 그래픽을 구현하는 데 한계가 있다는 점이 분명해지자, 다른 방법들을 검토하기 시작했습니다.
처음에는 React Native 전용 3D 엔진을 사용하는 방안을 고려했습니다. react-native-threejs나 expo-gl 같은 라이브러리가 있긴 했지만, 유지 관리가 활발하지 않거나 플랫폼 간 호환성이 부족해 적용하기에는 안정성이 떨어지는 문제가 있었습니다.

#### 방법2. 네이티브 모듈을 직접 구현

다른 방법으로 네이티브 모듈을 직접 만들어 Three.js를 연결하는 방법도 생각했습니다. 이 경우 별도 구현이 필요하고 개인 프로젝트 범위를 고려했을 때 개발 시간과 유지보수 부담이 지나치게 커질 것으로 판단했습니다.

#### 방법3. React Native 안에 WebView를 연결하기

선택한 방법은 React Native 안에 WebView를 연결하고, 웹 기반의 3D 시뮬레이터를 실행하는 방식이었습니다.

> **WebView**는 앱 내부에 포함된 웹 브라우저로, HTML, CSS, JavaScript와 같은 웹 기술을 그대로 실행할 수 있는 공간입니다.

> **Three.js**는 JavaScript 기반의 3D 그래픽 라이브러리로, 원래는 복잡한 기술(WebGL 등)을 직접 다뤄야 하는 웹 환경에서 간단하게 3D 장면을 만들 수 있게 도와주는 도구입니다.

Three.js는 웹 환경에 최적화되어 있어, WebView 내부에서 복잡한 설정 없이 3D 그래픽을 구현할 수 있습니다. 복잡한 네이티브 연동 없이 웹 기술만으로 3D 구현이 가능하다는 점은 큰 장점이었습니다. React Native와 WebView 간의 역할이 명확히 구분되어 구조를 단순하게 유지할 수 있다는 점도 중요한 부분이었습니다. 이런한 이유로, WebView를 포함한 구조 안에 시뮬레이션 기능을 구현하기로 결정했습니다.

### 2.3 구현: WebView와 React Native 간 양방향 통신 구조

React Native 내부에 WebView를 연결하고, WebView 안에서 Three.js 3D 렌더링을 실행하는 구조를 채택했습니다.
두 환경의 역할을 분리함으로써 WebView는 렌더링에 집중하고, React Native는 사용자 입력과 상태 관리 역할을 분리하여 담당하도록 설계했습니다.

이 구조에서 WebView와 React Native 간의 양방향 통신을 어떻게 구현할것인가였습니다. 두 환경은 서로 다른 실행 맥락에서 독립적으로 동작하기 때문에, 단순히 함수를 호출하거나 값을 전달하는 방식으로는 연결이 불가능했습니다.

시뮬레이션 장면을 구성하려면, 사용자가 입력한 가방 정보와 물건 목록을 WebView로 전달해야 하고, 반대로 WebView 내부에서 발생한 아이템 선택, 삭제 같은 사용자 동작을 다시 React Native로 알려주어야 합니다. 이처럼 양쪽 환경이 서로 실시간으로 정보를 주고받아야만 앱이 제대로 동작할 수 있었기 때문에, 통신 방식은 전체 구조의 핵심이었습니다.

이 문제를 해결하기 위해, WebView가 기본적으로 제공하는 통신 메서드인 postMessage와 onMessage를 활용해 두 환경 간의 양방향 통신 구조를 구현했습니다.

- **React Native → WebView** <br>
  사용자가 입력한 가방 정보 및 아이템 목록을 전달하여 3D 씬을 구성합니다.
- **WebView → React Native** <br>
  아이템 클릭, 삭제 등 사용자 인터랙션을 전달받아 상태를 갱신합니다.

아래는 실제로 사용된 메시지 전달 코드입니다.

```js
// React Native → WebView로 데이터 전달
webViewRef.current.postMessage(
  JSON.stringify({
    type: "RENDER_PACKING",
    payload: { items, bag },
  })
);

// WebView → React Native로 이벤트 전달
window.ReactNativeWebView.postMessage(
  JSON.stringify({
    type: "ITEM_SELECTED",
    payload: itemId,
  })
);
```

### 2.4 결과: RN 앱에서도 실시간 3D 시뮬레이션이 가능해졌다

WebView를 활용한 구조 덕분에, React Native 앱 환경에서도 실시간으로 3D 시뮬레이션 기능을 구현할 수 있었습니다.

웹 환경에서 사용하던 Three.js 기반의 3D 렌더링 방식을 모바일에서도 적용할 수 있었고, 복잡한 네이티브 연동 없이 다양한 물건을 배치해보며 수납 가능 여부를 직관적으로 확인할 수 있게 되었습니다.

## 3. 서버 구조 설계 및 예외 대응

가방의 사이즈 기준으로 시뮬레이션 화면을 보여주기 위해서, 신뢰할 수 있는 가방 사이즈 데이터가 필요합니다. YOLOv8 모델을 통해 이미지에서 물체를 탐지하는 것이 중심이었지만, 실제 서비스에서는 다양한 예외 상황을 고려해야만 안정적인 흐름이 완성됩니다. 이를 위해 FastAPI 기반의 백엔드 서버를 구조화된 모듈로 설계하고, 입력 검증 및 예외 대응 구조를 구현했습니다.

### 3.1 FastAPI 기반의 REST API 서버 구조
Python의 FastAPI 프레임워크를 사용해 RESTful한 API 서버를 구성했습니다. 주요 엔드포인트는 다음과 같은 역할을 합니다:

`/crawlImages`: URL을 기반으로 쇼핑몰 후기를 크롤링하고 이미지 리스트를 반환

각 엔드포인트는 Pydantic 스키마를 통해 요청 데이터를 검증하고, 결과를 구조화된 응답 형태(JSON) 로 반환합니다. 이렇게 스키마를 기준으로 API를 통일함으로써, 일관성을 유지할 수 있었습니다.

### 3.2 입력 검증 및 예외 상황 대응

현실의 후기 이미지 데이터는 매우 불완전합니다. 리뷰가 존재하지 않거나, 이미지가 없거나, 기준 객체가 없거나, 탐지에 실패할 수 있습니다. 이를 위해 다양한 상황에 대해 명확한 예외 처리 로직을 구성했습니다.

- URL 오류: 존재하지 않거나 접근이 불가능한 URL의 경우 400 에러 코드와 함께 설명 메시지 반환

- 이미지 없음: 후기 이미지가 하나도 수집되지 않은 경우 404 반환

- 가방 미검출: YOLO 탐지 결과 기준 객체는 감지되었으나, 가방이 존재하지 않는 경우 404

- 기준 객체 없음: 기준 객체가 없어 실측이 어려운 경우에는 카테고리 평균값을 보정값으로 사용

- 분석 실패: 모델 오류, 이미지 파일 손상 등 예상치 못한 실패에는 500 에러와 함께 원인 메시지 반환

이러한 예외 상황에서 에러 메시지로 끝나지 않고, 앱에서 사용자에게 안내 문구로 자연스럽게 연결되도록 처리됩니다. 예를 들어, 기준 객체가 없을 경우엔 사이즈를 직접 입력하는 대체 입력 폼으로 흐름을 전환하도록 설계했습니다.

### 3.3 서버 구조의 유지보수성과 확장성 고려
백엔드 코드는 다음과 같은 기준으로 모듈화되어 구성되었습니다:

`schemas/`: Pydantic 기반 요청 및 응답 스키마 정의

`routers/`: API 라우팅과 컨트롤러 기능

`services/`: YOLO 모델 호출, 이미지 분석, 데이터 가공 등 로직 처리 담당

`utils/`: 이미지 전처리, 예외 메시지, 로깅 등 공통 기능

`main.py`: 서버 진입점 및 라우터 등록

이 구조 덕분에 각 기능의 책임이 명확히 분리되어 있으며, 크롤링 대상 쇼핑몰을 추가하거나 새로운 YOLO 모델을 교체할 때도 최소한의 수정만으로 확장할 수 있습니다.


## 4. 앱 사용 흐름 구축

사용자가 쇼핑몰 URL만 입력하면, 그 뒤로는 자동으로 크롤링 → 이미지 분석 → 사이즈 추정 → 3D 시뮬레이션까지 이어지는 전체 흐름을 처리합니다.

### 1단계. 사용자가 쇼핑몰 URL 입력
앱의 메인 화면에서 사용자는 구매를 고려 중인 가방 상품의 URL을 입력합니다. 현재는 무신사와 지그재그를 지원하고 있으며, 입력된 URL은 서버로 전달됩니다.

```js
// URL 예시
https://store.musinsa.com/app/goods/123456
```

### 2단계. 서버에서 후기 이미지 크롤링
서버는 URL에서 상품 ID를 추출한 뒤, 해당 쇼핑몰의 후기 이미지 페이지를 크롤링합니다.
쇼핑몰마다 HTML 구조와 로딩 방식이 달라, 사이트별 맞춤 크롤링 로직을 사용합니다.

- 결과: 후기 이미지 리스트
- 예외 처리: 이미지가 없는 경우, 사용자에게 직접 입력을 유도합니다.

### 3단계. YOLOv8 모델 기반 이미지 분석
수집한 이미지들을 Python 서버로 전달하고, YOLOv8 모델을 사용해 가방과 비교 기준이 되는 객체를 동시에 탐지합니다.

- 비교 기준이 되는 객체가 있을 경우 → 상대 크기를 계산해 실제 사이즈 추정
- 비교 기준이 되는 객체가 없을 경우 → 카테고리별 평균값을 기반으로 보정
- 이미지가 없거나 가방이 미검출된 경우 → fallback으로 사용자 입력을 유도

### 4단계. 사이즈 추정 결과 반환
이미지 분석 결과는 다음과 같은 JSON 형태로 반환됩니다:

```json
{
  "width": 28.5,
  "height": 33.0,
  "depth": 14.2,
  "source": "image_analysis",
  "confidence": 0.87
}
```

이 결과는 클라이언트로 전달되어 앱 내 상태에 저장되고, 즉시 시뮬레이터에 반영됩니다.

### 5단계. WebView 기반 3D 시뮬레이터 실행
React Native 앱 내 WebView에 Three.js로 구현된 3D 시뮬레이터가 탑재되어 있습니다.

- React Native → WebView: 가방 사이즈와 아이템 목록 전달

- WebView → React Native: 아이템 삭제, 위치 변경 등 사용자 인터랙션 전달

이 구조를 통해 사용자는 가방 모델을 회전하거나, 다양한 아이템을 추가/삭제하며 수납 가능 여부를 직관적으로 확인할 수 있습니다.

### 6단계. 시뮬레이션 결과 저장 및 반복 사용

사용자가 시뮬레이션 화면에서 수정한 아이템 배치나 사이즈 정보는 앱에 저장되어 재사용할 수 있습니다.
자주 사용하는 아이템은 프리셋으로 제공되어 반복 입력 없이 시뮬레이션을 빠르게 실행할 수 있습니다.

소쿠리 앱은 URL 입력만으로 이미지 수집, 사이즈 분석, 3D 시각화를 자동으로 처리하는 파이프라인을 제공합니다. 사용자는 복잡한 설정 없이 직관적으로 가방 수납 시뮬레이션을 경험할 수 있습니다.

# Trouble Shooting

## 1. WebView 내 3D 시뮬레이터가 화면 밖에 렌더링되는 문제

초기 로딩 시, **가방 모델이 사용자 화면에 보이지 않는 현상**이 발생했습니다.

React Native 앱의 WebView 내부에서 Three.js로 3D 장면을 렌더링할 때, **모델은 정상적으로 로딩되었지만 화면에는 아무것도 표시되지 않았습니다.** 개발자 도구로 확인해 보니, **가방 모델은 씬 내부에 존재했지만 카메라가 올바른 방향을 바라보지 않아 화면 바깥에 렌더링되고 있었던 것이 원인**이었습니다.

이 문제는 **렌더링 타이밍과 카메라 위치 계산 시점이 분리되어 있었기 때문에 발생했습니다.** 아이템이 여러 개인 경우, 모든 모델이 로딩되기까지 시간이 필요한데, 카메라는 그보다 먼저 위치를 고정해 **초기 시점에서 장면 구성이 어긋나는 현상**이 나타났습니다.

이를 해결하기 위해, 보정 로직을 적용했습니다.

- 모든 아이템 및 가방이 로딩된 이후 **BoundingBox** 정보를 계산
- 해당 BoundingBox의 중심점과 크기를 기준으로 **카메라 위치를 재설정**
- **fitToView** 방식으로 씬 전체가 자동으로 중앙에 들어오도록 시야를 조정

> **BoundingBox**는 3D 모델이 차지하는 전체 영역을 감싸는 가상의 박스이며,
> **fitToView**는 경계 박스를 기준으로 카메라의 거리와 방향을 자동으로 조정해 모델이 화면 안에 보여지도록 맞춰주는 기능입니다.

로직을 적용한 이후 가방이나 아이템이 화면 중심에 렌더링되어, 사용자가 화면을 열었을 때 정상적으로 시뮬레이션 기능을 제공할 수 있었습니다.

<br>

## 2. WebView가 메세지에 응답하지 않는 문제

React Native에서 메세지를 보내도 WebView가 아직 초기화되지 않아 메시지를 무시하는 현상이 발생했습니다.

React Native와 WebView 간의 데이터 전달은 WebView가 기본적으로 제공하는 통신 메서드인 postMessage와 onMessage 메서드를 통해 이루어집니다. 그러나 실제 환경에서는 React Native 앱이 WebView를 마운트하자마자 메시지를 보내는 경우가 있어, WebView 측 스크립트가 아직 준비되지 않은 상태에서 메시지가 전달되어 무시되는 문제가 발생했습니다.

초기에는 메시지 형식 오류나 WebView 측 처리 지연을 의심했습니다. 이를 보완하기 위해 React Native에서 메시지를 보낼 때 일정 시간 지연시키는 debounce 방식을 적용해보았습니다.

```js
// React Native에서 메시지 전송을 지연
setTimeout(() => {
  webViewRef.current.postMessage(
    JSON.stringify({ type: "RENDER_PACKING", payload: { items, bag } })
  );
}, 300);
```

하지만 이 방식은 WebView에서 초기 렌더링이 안되는 현상을 해결하지 못했습니다. WebView가 준비되는 시점을 정확히 보장할 수 없기 때문에, 일정 시간 대기하는 방식만으로는 해결이 어려웠습니다.

해결을 위해, 통신 흐름을 반대로 변경했습니다. 준비가 완료되면 WebView에서 React Native에 신호를 먼저 보내도록 구조를 변경하였습니다.

```js
// WebView 내부 초기화 코드
window.onload = () => {
  window.ReactNativeWebView.postMessage(JSON.stringify({ type: "WEBVIEW_READY" }));
};
```

React Native 측에서는 해당 메시지를 수신한 이후에만 시뮬레이션 데이터를 전달합니다

```js
// React Native에서 'WEBVIEW_READY' 수신 후 메시지 전송
onMessage = (event) => {
  const { type } = JSON.parse(event.nativeEvent.data);
  if (type === "WEBVIEW_READY") {
    webViewRef.current.postMessage(
      JSON.stringify({
        type: "RENDER_PACKING",
        payload: { items, bag },
      })
    );
  }
};
```

이 구조를 적용한 이후, WebView가 완전히 초기화된 이후에만 메시지를 전달할 수 있게 되어, 초기 렌더링 실패나 무반응 이슈가 발생하지 않게 되었습니다.

# User Experience

앱은 손으로 직접 터치하고 즉시 반응을 확인할 수 있습니다. 사용자 관점에서 편리하고 직관적인 상호작용을 앱 안에서 구현하는 것이 목표였습니다.

## 어떤 기준으로 사용자 흐름을 설계할까?

UX 설계는 처음 사용하는 사용자도 기능을 쉽게 이해하고 자연스럽게 사용할 수 있도록 구현하는 것을 목표로 했습니다. 다음 세 가지를 기준으로 구현했습니다.

- **즉각성**: 터치 입력에 대한 반응은 지연 없이 발생해야 합니다.
- **예측 가능성**: 삭제나 추가 같은 동작은 사용자가 예상한 방식으로 동작해야 합니다.
- **명확한 피드백**: 사용자 관점에서 상태 변화나 오류는 시각적으로 명확하게 전달되어야 합니다.

## 4. 사이즈 수정 후에도 시뮬레이터와 항상 동기화되도록 적용

<p>
  <img width="300" src="https://github.com/user-attachments/assets/8068d693-7049-4dc9-834e-d1a552d91008" />
</p>

사용자는 가방이나 아이템의 크기를 언제든지 수정할 수 있어야 하고, 수정된 정보는 시뮬레이터에도 즉시 반영되어야 합니다.

- 각 아이템 카드를 약 2초 길게 누르면 사이즈 수정 모달을 호출할 수 있습니다.
- 수정된 값은 RN 상태에 저장되며, WebView로 전달되어 3D 모델이 리렌더링됩니다.
- 동일한 구조는 가방 사이즈 수정에도 적용되며, 전체 packing 영역이 자동으로 리사이징 됩니다.

이때 가장 중요했던 점은 아이템 리스트와 시뮬레이터 간의 상태 동기화 문제였습니다.
수정된 크기가 WebView에 반영되지 않거나, 반대로 WebView의 상태가 앱과 불일치할 경우 화면에 보이지 않게 됩니다.

이를 방지하기 위해 WebView로 메시지를 보낼 때는 항상 RENDER_PACKING 명령으로 전체 state를 전달하고,
수정, 삭제 등의 변경 액션은 UI와 WebView 양쪽에 동시에 적용되도록 구성했습니다.

# Retrospective

이번 프로젝트를 통해 입력부터 시뮬레이션까지의 전체 흐름을 직접 설계하고 구현하는 경험을 쌓을 수 있었습니다. React Native 환경에서 WebView와 Three.js를 연동하여 3D 시뮬레이션을 구현하는 과정은 기술적으로 도전적이었지만, 적용가능한 여러 방법들을 찾아보며 모바일 환경에서도 동작하도록 구현할 수 있었습니다.

구현 과정에서 특히 의미 있었던 부분은, 제스처 기반 인터랙션과 실시간 상태 동기화를 구현한 경험입니다. 사용자가 아이템을 추가, 수정, 삭제하는 기능을 구현하는 과정에서 직관적인 피드백을 제공하기 위해 다양한 제스처와 상태 전달 구조를 적용해보았습니다. 이를 바탕으로 React Native와 WebView 간 메시지 동기화를 구현하였습니다. 추후에는 피드백의 명확성과 크롤링 과정에서 속도를 개선하여, 사용자 관점에서 매끄러운 흐름을 구현해보고자 합니다.

현재는 이미지 기반 분석 또는 수동 입력을 통해 가방 크기를 추정하지만, IOS 카메라를 활용해 실제 가방을 실측할 수 있다면 사용자는 더 직접적이고 정확한 정보를 얻게 될 것입니다. ARKit을 통해 실측 기반의 시뮬레이션 입력 흐름을 추가하고, 이미지가 없는 상품이나 사용자 소지품 기반 커스터마이징 기능으로 확장해보고 싶습니다.

이번 프로젝트에서는 공개된 모델을 활용해 기준 객체와 가방을 탐지했지만, 추후에는 자체 데이터셋 기반으로 모델을 학습시켜 감지 정확도를 높이는 방향을 고려하고 있습니다. 실제 사용 환경에 최적화된 모델을 구성함으로써, 보다 안정적이고 신뢰도 높은 결과를 만들어보고 싶습니다.

이번 개인 프로젝트를 통해 다양한 기술 스택을 실제로 구현해보고, 시뮬레이션 시스템에 필요한 메시지 설계와 상태 구조, 사용자 피드백 구조에 대해 구체적으로 고민할 수 있었습니다.
